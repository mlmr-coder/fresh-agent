# Lingo 能力加载机制（技能 / 专家 / 连接器）

> **采集时点**：`main @ 8d312f3`（2026-09-10 13:33），CodeWhale 子模块 `f853f8f15`（2026-09-01）。
> **适用范围**：`pinvou3-app/`（Tauri 2 + React 桌面端）+ `CodeWhale/`（Agent 底座子模块）。
> 文中所有目录、字段、行为均可回溯到具体文件与行号。

---

## 0. 一句话总览

Lingo 把「模型能用的一切外部能力」统一收敛成三种形态，共用一套治理层：

```
能力面 = 原生工具家族（编译期，不可关）
       + 能力包线（运行期，用户可关）= 技能 Skill / 专家 Persona / 连接器 Connector
```

- **技能**：一段可按需加载的工作流程文本（`SKILL.md`），模型自己决定要不要读。
- **专家**：一张带完整人设正文的角色卡，挂载到会话改变模型行为方式。
- **连接器**：真的外部能力（MCP 工具、外部 API、CLI、授权流程）。

三者**加载器互不共享**，但在 UI 层（能力中心）与治理层（开关、模式 scope）是统一的。
见 `docs/capability-governance.md:19-32`。

```
│   └── personas/        用户自创专家卡       paths.rs:300
├── bundles/<pkg-id>/    市场安装 / 上传导入的包（一个包一个目录）
│   ├── mcp/             MCP manifest + server 脚本

│   └── installed.json   包登记信息
├── bundle/              内置释放区

│   ├── mcp.json         ★ 唯一 MCP 配置文件  paths.rs:361
│   └── personas/        内嵌专家卡（编译期资源，非运行时写入）
├── sessions/<sid>/
│   ├── skills/          ★ 会话技能组合目录（引擎唯一发现根）paths.rs:457
│   ├── persona.json     当前会话绑定的专家
```

> **注意**：代码里只有 `pinvou3` 命名，**没有任何「 Lingo 」路径**——产品显示名改了，
> 技术标识按 `docs/branding.md` 保留原样。

### 1.2 统一包模型（Bundle）

一切外部能力建模为一个包，三个部分均可空（`docs/capability-governance.md:67-84`）：

```
Bundle = { id, name, mcp_servers: [], skills: [], cli: [] }
```

| 形态 | 内容 | 例子 |
|---|---|---|
| 纯 MCP 包 | 仅 `servers` | weather、obsidian（本地 stdio）；qcc、canva-mcp（远程 OAuth） |
| 组合包 | `servers` + `skills` | MCP 函数 + 使用引导一体 |
| CLI 包 | 仅 `cli` | 飞书 / 企微 / 钉钉 / 腾讯会议 / ima |
| 纯技能包 | 仅 `skills` | 市场预置、用户上传、手放技能 |

两个关键设计纪律：

1. **包类型不存存储标签，由内容现算**（`bundle_kind` 推导）。理由写在
   `capability-governance.md:78-80`：不可信输入（项目技能、上传包）自报的标签是
   提权通道，分类事实只能由安装/加载层（可信代码）推导。
2. **一个包 = 一个开关**。包内技能（原 companion skill）没有独立开关，可见性唯一
   跟随所属包——不存在「引擎在、引导不在」的半截状态（`:82-84`）。

### 1.3 模式 scope

所有开关按 **会话模式（SessionMode）** 持久化，当前两个：`plain`（普通聊天）、
`code`（代码模式）。模式是**编译期封闭集合**，不允许运行期自定义
（`capability-governance.md:166-167`）。

默认安全姿态由模式身份决定（`core/session_mode.rs::pack_default_policy()`）：

| 模式 | 默认策略 | 含义 |
|---|---|---|
| plain | `AllowAll` | 全开 |
| code | **`DenyAll`** | 全禁——外部能力需显式开启，收敛泄露面与攻击面 |

### 1.4 唯一的开关存储

`~/.pinvou3/disabled_bundles.json`，键 = 包 id（`capability-governance.md:88-99`）：

```json
{
  "scopes":          { "<mode>": ["<包 id>"] },
  "hidden_scopes":   { "<mode>": ["<包 id>"] },
  "initialized":     ["<mode>"],
  "project_skills_enabled": false
}
```

`scopes`（开关）与 `hidden_scopes`（可见性）是**正交的两道门**：

- 对模型的实际供给取**并集** `unavailable = disabled ∪ hidden`（`unavailable_bundles_for`）；
- `hidden` 只决定包是否出现在选择列表，不决定 on/off；
- `disabled` 只决定开关态，不影响列表可见性。

用户数据语义（三条线一致，`:124-129`）：某 scope 无记录 → 回落编译期默认；用户首次
toggle 时物化整个 scope 列表落盘 → 此后**冻结**，产品默认调整不穿透已做过选择的用户。

## 2. 技能（Skill）加载机制

### 2.1 五种来源与扫描目录

来源顺序见 `features/assistant/skill_materialization.rs:40-58` 的 `skill_source_dirs()`，
**first-wins（高优先级在前）**：

| 优先级 | 来源 | 绝对路径 | 说明 |
|---|---|---|---|
| 0（最高） | **项目级** | `{ws}/.agents/skills`、`.pinvou/skills`、`skills`、`.opencode/skills`、`.claude/skills`、`.cursor/skills`、`.codewhale/skills` | 仅 code 模式 + 开关开启时扫描 |
| 1 | **用户手放** | `~/.pinvou3/user/skills/` | 覆盖市场安装 |
| 2 | **市场安装** | `~/.pinvou3/bundles/<pkg-id>/skills/` | 按包聚合（Phase 2 第十刀起） |
| 3（最低） | **内置释放** | `~/.pinvou3/bundle/skills/` | 仅 visual-design 等非市场包 |

项目级目录见 `skill_materialization.rs:66-79`。**项目级默认关闭**，因为项目内文本是
prompt-injection 面，信任级别与装机技能不同（`:76-79`）。

内置资源是编译期 `include_str!`/`include_dir` 内嵌，启动时解包：

```rust
// runtime_bundle/platform/mod.rs
include_dir!(".../builtin-skills/visual-design")     // :277
// lark 9 个域（:19-24）、wecom / dingtalk / tmeet（:40/45/51）
// 市场预置：resources/common/skill-marketplace/（pptx、visualizer、ima-skills…）
```

解包落点 `extraction.rs:544/573/600/623`。

> **CodeWhale 底座自带技能不生效**：`CodeWhale/crates/tui/assets/skills/`
> （research / dataviz / fleet-manager）是 TUI 用的，桌面端不加载。
> 原因见 §2.6 的 fork 改动 T3。

### 2.2 发现与 SKILL.md 解析

底座 `SkillRegistry::discover` → `discover_recursive`
（`CodeWhale/crates/tui/src/skills/mod.rs:348-381, 383+`）：

- 递归深度上限 8（`:327`）；
- 跳过 `.` 开头的隐藏目录（`:425-429`）；
- 只有 root 读失败才告警，子目录读失败静默跳过（`:398-412`）。

**frontmatter 解析是手写平铺 YAML 解析器** `parse_skill`（`:533-748`），
不是 `serde_yaml`，支持 `|` / `>` 六种块标量与 chomping 指示符（`:562-663`）。

```yaml
---
name: my-skill                 # 必填（:681-685）
description: 一句话说明        # :687
invocation: explicit           # :689-690（ExplicitOnly 不进模型索引）
description_zh: 中文说明       # :701-710 本地化变体
---
```

容错（`:726-747`）：缺 frontmatter 时回退取首个 `# Heading` 当名字；
名字非法则规范化并告警（`:520-531`）。

> ⚠️ 与 WorkBuddy 那套 `SKILL.md` 字段**不同**：这里**没有** `read_when`、
> **没有** `agent_created`。跨生态搬运技能时 frontmatter 需改写。

App 侧另有一套用于市场展示的轻量镜像解析：`skill_marketplace.rs:1641-1659`，
注释明示「镜像 CodeWhale `parse_skill`」（`:1673-1679`）。

### 2.3 关键机制：会话组合目录（物化）

**这是 Lingo 技能加载最特别的一环。** 底座不直接扫上面那堆来源目录，而只扫一个目录——
`~/.pinvou3/sessions/<sid>/skills/`。App 负责把多来源按优先级**拷贝**过去。

```
用户/项目/市场/内置 多来源目录
        │  enabled_skills_for(scope, workspace)  按优先级 first-wins
        ▼
  copy_skill_dir 逐个物理拷贝（:181-198）
        │  staging + rename 原子替换（:221-238）
        ▼
~/.pinvou3/sessions/<sid>/skills/   ← 底座 SkillRegistry 唯一发现根
```

物化时机是三段式的（`skill_materialization.rs`）：

| 时机 | 函数 | 触发 |
|---|---|---|
| 会话 spawn | `materialize_session_skills`（`:210`） | 建会话时全量 |
| 开关变化 | `rewrite_session_skills`（`:245`） | 事件增量重写 |
| 发送前自愈 | `ensure_session_skills`（`:289`） | 发送路径兜底 |

物化的好处：开关变化**不用 respawn 引擎**，改目录内容 → 底座按 mtime 缓存失效 →
下一轮重扫即可（见 §5.2）。

### 2.4 渐进式加载（Progressive Disclosure）

**只加载索引，不加载正文。** 底座 `render_skills_block`
（`CodeWhale/crates/tui/src/skills/mod.rs:1339-1472`）把 `name + description`
渲成 `## Skills` 块塞进系统提示：

```
## Skills
Skills are optional local instruction packs. This budgeted index exposes
routing metadata; skill bodies stay unloaded.

### Available skills
- my-skill: 一句话说明
...

### Usage
- When the user names a skill or specialized instructions may help, call
  `load_skill` with `name="list"`; load the exact skill before applying it.
- Do not carry a skill across turns unless re-mentioned. Skill instructions
  do not expand tool, approval, or trust authority.
```

预算硬约束（`mod.rs:42, 47`）：

- 单条 description 截断 **280 字符**；
- 整块硬预算 **2400 字符**，溢出打省略计数；
- registry 为空 → 返回 `None`，`## Skills` 块**整体不渲染**（`:1340-1342`）；
- `invocation: explicit` 的技能**不进索引**（`:1381-1386`），避免成为 ambient 指令。

正文由模型调 `load_skill` 工具按名读取（`CodeWhale/crates/tui/src/tools/skill.rs:30-190`，
`name="list"` 列全量 `:102-121`，正文 `:169`），返回 `companion_files`（`:292`）
让模型再用 File read 取兄弟文件。

**发现缓存**：`discovery_cache()` 是 `HashMap<Vec<PathBuf>, DiscoveryCacheEntry>`，
上限 8 条（`mod.rs:1078-1083`），命中时只 re-stat 受监视路径的 mtime + len
（`:1102-1109`）。

### 2.5 技能内容如何真正生效

**不注入 system prompt 正文**——只注入索引；模型自己调 `load_skill` 才把正文拉进上下文。

`scripts/` 目录**没有专用 runtime、没有沙箱、没有超时控制**：脚本就是普通文件，
由模型经 `Bash` 执行，受 execpolicy 约束（trust_mode=true，`bridge.rs:1569`）。

被禁用技能的脚本会逐个生成 Deny 规则（`bridge.rs:1950-1969` + `:2604-2625`），
解释器映射 py / sh / js / ps1（`:2649-2660`）。

### 2.6 与 CodeWhale 底座的分工

| 能力 | 归属 |
|---|---|
| SkillRegistry、frontmatter 解析、索引渲染、`load_skill` 工具、发现缓存、roots 枚举、审计 | **底座**（`CodeWhale/crates/tui/src/skills/`） |
| 组合目录物化、双 scope 开关、市场安装/导入、包模型、execpolicy deny | **App**（`pinvou3-app/src-tauri/src/features/`） |

**关键 fork 改动 T3**：「Skill 只从宿主显式 `skills_dir` 扫描」，砍掉底座的 workspace
并集发现（`docs/fork-modifications.md:159-170`，实现 `mod.rs:987-997`）。
所以 App 必须在物化阶段就把多来源拼好——底座不会自己去 workspace 找。

| 入口 | 命令 | 位置 |
|---|---|---|

包结构规范见 `docs/plugin-package-spec.md`：

```

├── plugin.json          # 权威声明（纯单组件可省略，走结构回退 §5）
```

## 3. 专家（Expert）加载机制

### 3.1 代码里叫 Persona，不叫 Expert

全仓库 **没有** `ExpertPack` / `expertId` / `AGENT.md`。实现在
`pinvou3-app/src-tauri/src/features/personas/mod.rs:1`——「专家面具池（卡牌池）」。

> ⚠️ WorkBuddy 侧的 `expert-manager` 技能（「从开源仓库创建专家包」）在本仓库
> **无任何对应实现**，那是另一套生态的东西。

### 3.2 两个来源

| 来源 | 数据 | 加载 |
|---|---|---|
| **内嵌 agency-agents-zh**（`source="builtin"`） | `resources/common/bundle/personas/agency-agents.json`，schema `agency-1.0`，**261 张卡**，MIT（jnMetaCode/agency-agents-zh@6e158d9c） | 编译期 `include_str!`（`mod.rs:21-22`）+ `OnceLock`（`:85`） |
| **内置卡**（`source="builtin"`） | 「卡牌制造专家」，见 `builtin_extra()`（`:323-337`） | 同上 |
| **用户自创**（`source="user"`） | `~/.pinvou3/user/personas/<id>.json`（`paths.rs:300`） | `RwLock`（`:87`）+ `USER_REVISION: AtomicU64`（`:89`） |

用户卡**永不被 bundle 覆写**（`:298-299`）。CRUD 后 `reload_user()` 重扫磁盘并
递增版本号（`:136-145`）——先发布卡池内容，再推进版本，Acquire 读到新版本时必然
能看到新卡。

### 3.3 卡片结构

```rust
// personas/mod.rs:29-51
pub struct PersonaCard {
    pub id: String,
    pub dept: String,        // 部门，前端 facet 按此分组
    pub name: String,
    pub description: String,
    pub emoji: String,
    pub color: String,
    pub body: String,        // ★ 完整人设 markdown（~6K 字）
    pub source: String,      // "builtin" | "user"
    #[serde(skip)]
    pub conversational_only: bool,  // 戴卡时清空工具表（元卡专用）
}
```

`list_personas` 返回**不含 body** 的 `PersonaSummary`（`:58+`），避免 1.2 MB body
全量下发；body 在加持或查看详情时按需取（`read_persona_body`）。

### 3.4 注入机制：一次全量 + 每轮锚点

人设正文太长（~6K 字），不能每轮灌。机制写在 `personas/mod.rs:11-13`：

```
加持 equip_persona
   → set_session_persona(..., equip_body_injection(card))
   → 存 pending_persona_body（features/sessions/mode_state.rs:435-460）
   → 首条消息时一次性 prepend 完整 body（app/commands/chat.rs:209-216）
   → 之后每轮只注入轻量锚点 equip_anchor（engine_pool.rs:2017）
```

会话绑定持久化在 `~/.pinvou3/sessions/<sid>/persona.json`。恢复历史会话时
**必须重新注入正文**，仅恢复挂件不能替代运行时恢复
（`docs/capability-center.md:5`）；`persona_events.json` 只用于展示历史。

### 3.5 多智能体委派（Fleet）

`features/assistant/expert_roster.rs` 把专家池投影成 CodeWhale Fleet 配置
（注释即「Pinvou 专家池到 CodeWhale Fleet 配置的纯内存投影」）：

- `ExpertRosterSnapshot::capture()` 按版本号缓存快照（`:33-75`）；
- role 名 `exp-<slug>`（`:154-171`）；
- 每轮提醒只列 **≤20 条短候选** `available_role_lines`（`:120-133`）；
- 完整正文**只注入被派中的子智能体**，由底座
  `CodeWhale/crates/tui/src/tools/subagent/mod.rs:11763 spawn_profile_prompt_overlay` 完成。

### 3.6 与技能的区别：完全不共享加载器

| | 技能 | 专家 |
|---|---|---|
| 载体 | 磁盘目录 + `SKILL.md` | 内存 JSON 卡 |
| 发现 | `SkillRegistry` 扫 `skills_dir` | `OnceLock` + `RwLock`，扫 `user/personas/*.json` |
| 注入 | 索引进系统提示，正文按需 `load_skill` | 首轮完整 body，之后轻量锚点 |
| 开关 | 按 scope 的 `disabled_bundles.json` | 会话级单选，无 scope 开关 |
| 底层通道 | `EngineConfig.skills_dir` | `fleet.profiles` |

`bundle/instructions.md`（`paths.rs:46`）是另一回事——全局指令文件。
`/` slash 命令只出自技能，与专家正交。

## 4. 连接器（Connector）加载机制

### 4.1 两层分工

```
CodeWhale 底座：MCP 协议 / 传输 / 握手 / 工具发现 / tools-call / OAuth 引擎
      ↕ 唯一契约面：~/.pinvou3/bundle/mcp.json + 一个 secret resolver 钩子
Lingo App：市场目录、安装卸载、配置生成、密钥治理、按 scope 的开关与可见性
```

### 4.2 四类来源

**① 内置预置（编译期内嵌）** — `features/marketplace/mcp_catalog.rs:22-109`，
`MCP_PACKAGES` 共 **11 个**：

### 4.4 连接流程

启动时序（`bridge.rs:298-320`）：

```
install_mcp_secret_resolver()
  → paths::ensure_dirs()
  → bundle.ensure_extracted()
       ├── write_mcp_servers        （extraction.rs:1117）
       └── ensure_builtin_mcp_servers（:680，每次启动 upsert 内置 server、
                                        坏 JSON 自愈、旧路径迁移）
  → engine spawn（mcp.json 路径注入 bridge.rs:1840）
```

连接是**惰性**的（`get_or_connect`），不是启动即连。握手 `mcp.rs:2010-2047`：

```jsonc
{ "protocolVersion": "2024-11-05",
  "clientInfo": { "name": "codewhale-tui" },
  "capabilities": { "tools": {}, "resources": {}, "prompts": {} } }
```

回包解析 capabilities（`mcp.rs:1170`）后发 `notifications/initialized`，
随后 `discover_all`（`:2050`）分页拉全 `tools/list`（`discover_tools:2103`，有
catalog budget 上限），resources/prompts 按能力门控且失败不致命。

超时：connect **10s** / execute **60s** / read **120s**（`mcp.rs:539-547`），
server 级可覆盖（`:582-586`）。`required: true` 的 server 初始化失败直接报错（`:3097`）。
stale session 自动 drop + 重连重试一次（`:3712-3736`）。

### 4.5 鉴权

**OAuth 2.0 授权码 + PKCE + 动态客户端注册（DCR）**，由 rmcp 的
`AuthorizationManager` / `AuthorizationSession` 承担（`oauth.rs:12-13`、`:897`）。
支持 RFC 8707 `resource`（`mcp.rs:642-643`）。

回调是**本地 loopback TCP**，不是深链：`http://127.0.0.1:<port>/callback`
（`oauth.rs:1068-1092`），绑定 host 受 `callback_bind_host` 限制为 localhost 或显式指定。
全仓库未见 `workbuddy://` 一类 scheme。

Token 持久化在 **OS keyring**：`codewhale_secrets::Secrets::auto_detect()`，
默认 service 名 **`deepseek`**（`CodeWhale/crates/secrets/src/lib.rs:26`），
键名 `mcp_oauth_<sha256(server|url)>`（`oauth.rs:656-685`）。

**Bearer / API Key 不落明文**：`mcp.json` 只写 `${PINVOU3_MCP_SECRET_<KEY>}` 占位
（`secrets.rs:92-109`），真实值在 keyring service `pinvou3-mcp-secret`
（`credential_store.rs:84`）+ 进程内注册表 `MCP_SECRET_VALUES`（`secrets.rs:32-33`）。

运行时**不写进程 env**（edition 2024 的 `set_var` 竞态），改由底座钩子查询：

```rust
// features/marketplace/mod.rs:400-404 → CodeWhale mcp.rs:53-59
install_mcp_secret_resolver(...)  // ${...} / env_headers / bearer_token_env_var
                                  // 优先查进程内回调，未命中回落进程 env
```

这条 fork 契约由 `scripts/fork-guard.sh:109,158` 卡住，测试
`forkguard_mcp_secret_resolver_supplies_values_without_process_env_writes`。
官方记录 `docs/fork-modifications.md:132`。

### 4.6 工具调用与审批

工具命名 `mcp_{server}_{tool}`（`mcp.rs:3111-3113`）。`parse_prefixed_name`
（`:3387-3415`）**只认服务端已 advertise 的目录**，重名直接歧义报错——防止工具名伪造。

**没有 per-MCP-tool 审批 UI**：`session_policy.rs:184` 返回
`(auto_approve=true, ApprovalMode::Auto)`，测试断言「两模式本期必须全自动」（`:325-330`）。
控制手段是**安装时一次性授权 + 运行时开关**，而非逐次确认。硬拦截靠 execpolicy
ruleset（`bridge.rs:1833`），由 `refresh_permission_rulesets()` 热刷。

## 5. 治理：开关如何真正生效

### 5.1 生效通道

```
开关变化
  → 持久化 disabled_bundles.json
  → 重算投影 unavailable = disabled ∪ hidden
  → 组合目录重写（技能部分）
  → disallowed_tools 热刷（MCP 部分）
  → 事件广播（remote_control:tools_changed）
```

`capability-governance.md:135-145`。注：文档里规划的**唯一失效入口**
`capability_changed` 尚未实施，现状是各开关命令分别触发刷新（`:161`）。

### 5.2 会话中关闭的边界（重要）

`## Skills` 块在系统提示里，底座**每轮重拼**系统提示（发现走 mtime 缓存，
组合目录一变下一轮即失效重扫），所以禁用后**新轮次**不再列出该技能、后续
`load_skill` 也读不到正文。

**但已进入上下文的内容撤不回**——若本会话此前已 `load_skill` 读过该技能，
其正文留在消息历史里，模型仍记得并可能继续按其引导作答。

因此供给层关闭是「体验层尽力而为」，真正的保证在**执行层**：

- execpolicy deny 硬拒该技能目录内脚本的 spawn；
- `disallowed_tools` 过滤 MCP 工具。

二者不依赖上下文是否已被污染。纯引导型技能（无脚本）在已被读入后无法从模型记忆中
擦除，这是 LLM 上下文的固有边界（`capability-governance.md:147-154`）。

### 5.3 底座硬防线（与上层状态无关）

```
白名单 allowed_tools（编译期，spawn 给定）
  → disallowed retain（deny 优先于 allow）
  → 执行门逐次校验（catalog 缺席 ⇒ 调用拒绝）
  → 审批分类（McpRead / McpAction 风险分级）
```

UI 或状态层出 bug 也放不出白名单外的能力。白名单在
`features/assistant/tool_policy.rs::PINVOU3_ALLOWED_TOOLS`，改动需 respawn，
属安全评审事项。

## 6. 安全边界

| 面 | 措施 | 位置 |
|---|---|---|
| 密钥落盘 | 只进 keyring，`mcp.json` 只写 `${...}` 占位 | `secrets.rs:92-109` |
| 日志泄露 | `redact_secret` / `redact_body_preview` | `mcp.rs:513` |
| 路径穿越 | 强制绝对路径 + `canonicalize` + `BLOCKED_COMPONENTS`（`.ssh`/`.aws`/`.env`/`id_rsa`/`credentials.json`）+ `BLOCKED_PREFIXES`（`/etc/shadow`、`/proc/`） | `path_policy.rs:19-44, 81-90` |
| zip bomb | 有界读 `read_zip_entry_bounded` + 200MB 上限 | `plugin_import.rs:36, 309-321` |
| 包名注入 | `is_safe_component_id` | `plugin_import.rs:123` |
| 脚本名注入 | `read_skill_body` 只留 `[A-Za-z0-9_-]` | `interaction.rs:370-376` |
| 依赖预检 | `pip install` 前先 importlib 预检 | `connectors.rs:89-100` |
| 子进程回收 | `kill_on_drop(true)`，stderr 64 行环形缓冲 | `mcp/stdio.rs:36-67, 107` |
| 仓库泄露 | `.gitleaks.toml` + `deny_sensitive_paths.{sh,ps1}` | 仓库根 |

**没有的**：
- 无 seccomp / landlock 等真正的进程沙箱；
- 无 `skills-security-check` 类安装前审计脚本（那是 WorkBuddy 生态的东西）；
- 技能脚本无专用 runtime / 超时，靠 execpolicy + `Bash` 通用约束。

**已登记的残余风险**：`bridge.rs:1944-1949` 注明 execpolicy DSL 无法表达目录前缀，
「拷贝后执行 / 引号变体」可绕过 deny 规则。

## 8. 已知限制与待办

1. **OAuth 远程包 readiness 恒 Ready**：远程 OAuth 包没有必填凭据声明，
   `readiness_for` 只查 credentials 必填项是否在系统凭据存储，因此恒报 Ready。
   **无法用 readiness 门控授权是否完成**（`capability-governance.md:213-219`）。
2. **工具名获取以 manifest 预测为主**：`model_tool_names` 按 `mcp_{server}_*` 前缀
   + manifest 声明生成禁用名单，而非查引擎实际暴露的 `model_name`。
   id 含连字符等情况会导致「禁不掉」（`:156-160`，已定方向未实施）。
3. **`tool_credentials` / `tool_config_fields` 不按 (key, target) 去重**：三路声明
   简单拼接，同一凭据可能重复出现在收集弹窗中（`:220-224`）。
4. **唯一失效入口 `capability_changed` 未实施**：现状各开关命令分别触发刷新（`:161`）。
5. **CLI 包真实执行面经 `Bash`**：开关只能隐藏引导，要封死需 Bash hook 拦截，
   当前作为已接受风险（`:196-198`）。
6. **会话中关闭上下文不可撤回**：见 §5.2。
7. **execpolicy 无法表达目录前缀**：拷贝后执行可绕过 deny（§6）。
8. **CodeWhale 底座技能不生效**：`CodeWhale/crates/tui/assets/skills/`（research /
   dataviz / fleet-manager）是 TUI 用的，桌面端不加载（fork T3 的副作用）。
